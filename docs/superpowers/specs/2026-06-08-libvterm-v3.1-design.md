# Decision record — terminal-hud engine: libvterm (v3.1)

**Date:** 2026-06-08
**Status:** Accepted
**Canonical spec:** [`SPEC.md`](../../../SPEC.md) (v3.1.0)
**Phase 0 evidence:** [`PHASE0.md`](../../../PHASE0.md)

This is the brainstorming decision record. The full design lives in `SPEC.md`; this file captures *why* the direction changed and what was decided.

## Context

terminal-hud needs a VT *state engine* — something that parses the hosted shell's output bytes into a readable grid + scrollback — so the program can own the screen and pin top/bottom bars around a scrolling middle. v3.0 chose libghostty-vt (via go-libghostty).

## What happened in Phase 0

Phase 0 (go/no-go) was executed on the target Mac (macOS 26.5.1, Apple Silicon). Three layers were peeled back:

1. Cloudflare blocked ghostty's dependency mirror from the corporate network → worked around with a phone hotspot.
2. ghostty pins Zig exactly 0.15.2 (Homebrew had 0.16.0) → worked around by downloading official Zig 0.15.2.
3. **Hard blocker:** Zig 0.15.2's only macOS linker (self-hosted Mach-O) is incompatible with the macOS 26 SDK — it emits libSystem `undefined symbol` errors and produces no library; LLD is unsupported for Mach-O in 0.15.2. Reproduced with a trivial empty Zig program, so it is not ghostty-specific.

Conclusion: **libghostty-vt is NO-GO on this machine** — a toolchain incompatibility, not an API problem. Unresolvable here without upstream moving off Zig 0.15.2.

## Options considered

| Option | Verdict |
|---|---|
| Wait for libghostty-vt (revisit when ghostty needs Zig ≥ 0.16) | Viable later; no progress now |
| Build libghostty-vt on macOS ≤ 15 / Linux, reuse artifact | Fragile, cross-machine |
| **Switch engine to libvterm** | **Chosen** |
| Fall back to v2.1 (scrolling top bar, no engine) | Sanctioned fallback; abandons true pinning |
| Enlightenment / EFL | Rejected — it's a Linux desktop + Terminology terminal, not an embeddable macOS-friendly VT engine; healthy but irrelevant to this role |

## Decision

Adopt **libvterm** (C99 VT engine behind Neovim's `:terminal`) as the v3.1 engine. Verified GO in Phase 0b: `brew install libvterm` (0.3.3) + a Go cgo program built and ran on macOS 26, parsed an SGR stream, and read the grid back (`"Hello, world!"`).

The v3 screen-owning architecture is unchanged; only the `engine` module swaps and grows two responsibilities libghostty-vt would have donated.

## Key decisions from brainstorming

- **Scrollback:** engine owns a bounded ring buffer fed by libvterm `sb_pushline`/`sb_popline`. Default cap **10,000 lines**, configurable.
- **Selection/copy:** our code over grid + ring buffer; yank via `pbcopy` (macOS) / OSC 52 (fallback).
- **Exit-code module:** custom OSC emitted by an **opt-in zsh precmd snippet**, parsed by the engine. Hidden if not installed.
- **Path module:** from OSC 7 cwd event; hidden if absent.
- **cgo callbacks:** routed via `cgo.Handle`; isolated in `engine/callbacks.go`; the only unsafe-adjacent unit.

## Accepted tradeoffs

- **No scrollback-history reflow on resize** (documented libvterm limitation; active screen does reflow).
- We own scrollback storage and selection (libghostty-vt provided both).

## In exchange we gain

- Builds today on macOS 26: plain C, `cc`, system package, no Zig, no network-fetched build deps, no exact-version toolchain pin.
- Stable API (libvterm frozen since 0.3) vs go-libghostty's explicitly-unstable API.

## Next step
